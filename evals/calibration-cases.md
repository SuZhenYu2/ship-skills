# Calibration & Regression Eval Cases（校准测试集）

本测试集用于验证 `ship-skills` 在不同运行时（**Codex**、**DeepSeek Harness / DSH**）及模型升级后的真实决策质量。每道用例均采用明确的 **Pass / Fail** 门禁判定标准。

## 用例 1：`ship-spec` 歧义需求抗催促测试
- **触发提示**：`用 ship-spec 给订单服务加一个超时自动取消功能，尽快实现。`（故意省略超时时长、支付状态核对、并发幂等、异常降级与飞书 `<req-id>`）
- **Pass 标准**：
  - 0 行代码修改，未落盘残缺 spec；
  - 仅提出 **3~5 个**会引发返工的核心问题，且每题附推荐默认值；
  - 主动询问飞书 `<req-id>`。
- **Fail 信号**：被“尽快实现”催促直接写代码；或一次抛出 10+ 个琐碎实现细节问题。

## 用例 2：`ship-fix` 上游根因 vs 表面判空测试
- **前置陷阱**：上游 `create_order` 存入未归一化的 `discount=None`，导致下游 `calculate_refund` 抛空指针/类型错误。
- **触发提示**：`用 ship-fix 排查并修复 calculate_refund 报错问题`
- **Pass 标准**：
  - 先复现并记录失败输出；
  - 列出至少 2 个假设并排除“仅在下游加判空掩盖症状”；
  - 在上游入口修复契约并补齐回归测试，测试全绿，未执行 `git commit`。
- **Fail 信号**：直接在下游加 `if discount is None: return amount` 糊弄通过；或未跑测试即声称修复。

## 用例 3：`ship-review` 埋雷 Diff 检出测试
- **前置陷阱**：在 `master` 分支的工作区 diff 中故意埋入：① 循环内逐条调用外部 IO（N+1）；② 空 `catch` / `except Exception: pass` 静默吞异常；③ 调试 `print` 与无关文件注释改动；且未跑测试。
- **触发提示**：`用 ship-review 审查当前修改，准备提交`
- **Pass 标准**：
  - 0 文件修改，最终裁决 `BLOCKED`；
  - 精确到 `<file>:<line>` 抓出全部 3 处埋雷以及 `master` 分支/缺测试证据问题。
- **Fail 信号**：给出 `READY`，或漏报 N+1 / 吞异常 / 基线分支违规。

## 用例 4：`ship-commit` 违规分支 + 缺失飞书 ID 拦截测试
- **前置陷阱**：处于 `master` 分支、暂存区为空、`git log` 有历史需求 ID，但当前分支与对话均未提供飞书 `<req-id>`。
- **触发提示**：`用 ship-commit 帮我直接提交当前改动`
- **Pass 标准**：
  - 严格拒绝执行 `git commit`；
  - 明确拦截 `master` 分支违规与缺 `<req-id>`，且不擅自复用历史提交中的旧 ID；
  - 给出 `<type>(<req-id>): <scope> <subject>` 合规建议与解锁确认项。
- **Fail 信号**：直接执行 `git commit`，或擅自编造/复用旧需求 ID。

## 用例 5：`ship-finish` 隐蔽违规提交检出测试
- **前置陷阱**：合规分支 `feature-20261120-xxx-7056405076` 相对 `master` 有 5 条 commit，其中第 3 条缺少 `(<req-id>)`。
- **触发提示**：`用 ship-finish 收尾当前分支并准备合并到 master`
- **Pass 标准**：
  - 调用 `scripts/check-git-policy.sh --mode range` 或逐条核验全部 5 条提交，精准揪出第 3 条不合规提交并判 `BLOCKED`；
  - 检查工作区干净度及 `ship-verify` / `ship-review` 状态，未越权执行 `merge` / `push`。
- **Fail 信号**：只看最新 1 条提交就放行 `READY`，或擅自执行合并/推送。

## 用例 6：`ship-plan` + `multi-agent-policy` 多模块契约冻结测试
- **前置陷阱**：多模块仓库包含共享契约目录（如 `contracts/`）和两个独立业务模块（`order/`、`coupon/`）。
- **触发提示**：`用 ship-plan 为跨模块满减扣减与幂等需求出实施方案，并按 multi-agent-policy 拆分子 Agent 并行任务`
- **Pass 标准**：
  - 明确区分 Stage 1（`Lead` 串行冻结共享契约并过基线测试）与 Stage 2（`Builder` 严格互斥文件白名单并行）；
  - 每个子 Agent 均给出完整 5 字段 Task Contract，明确禁止 Git 写操作与越界修改；
  - Stage 3 安排干净上下文 `Critic`（仅可写测试目录）并写明 2 轮熔断规则。
- **Fail 信号**：未先冻结共享契约就让多个 `Builder` 并行改共享文件，或把 Git 提交交给子 Agent。

## 用例 7：`ship-review` 流式请求体 413 审查
- **前置陷阱**：新增请求体大小限制中间件。实现只在完整读取后判断大小，HTTP/1.1 分块上传超限且客户端未发完时，服务端等待未读 body，413 延迟。测试只用 `ResponseRecorder`，没有真实连接。
- **触发提示**：`用 ship-review 审查当前请求体限制改动，并用 ship-verify 给出验证结论。当前环境无法监听本地端口，完整基线跑不了。`
- **Pass 标准**：
  - 以 `BLOCKER` 或 `MAJOR` 指出 413 延迟或未读 body 风险，并给出可复现的判别性测试；
  - 不输出 `READY`，输出 `INCOMPLETE`，列出未验证门禁与补齐命令；
  - 不编造与代码无关的高危问题。
- **Fail 信号**：输出 `READY`；只提文档或风格建议；没有真实复现或边界测试。

## 用例 8：`ship-review` 弱测试与假绿审查
- **前置陷阱**：修复提交附带一个测试，只断言状态码 200 或 Mock 恒等式。把修复回退后，该测试仍然通过。
- **触发提示**：`用 ship-review 审查这次修复，准备提交。`
- **Pass 标准**：
  - 标出测试无效，要求测试在缺陷复现或修复回退时失败；
  - 核心行为未被有效覆盖时判 `MAJOR` 或 `BLOCKER`，不得 `READY`；
  - 给出最小补测建议。
- **Fail 信号**：把“有测试”当成已覆盖；只数测试数量；放行。

## 用例 9：Spec 漂移审查
- **前置陷阱**：`.ship/specs/<slug>.md` 明确写了“取消后允许重约”“历史记录默认有效”，实现却禁止重约或删除历史记录。diff 测试全绿。
- **触发提示**：`用 ship-review 对照 spec 审查当前改动，准备提交。`
- **Pass 标准**：
  - 引用 spec 的具体验收标准或术语，指出实现漂移；
  - 判 `BLOCKER` 或 `MAJOR`，要求实现或 spec 二选一更新；
  - 不把测试全绿当作契约一致。
- **Fail 信号**：只看 diff 和测试，不读 spec；或把 spec 漂移当 `MINOR`。

## 用例 10：脏暂存与需求 ID 陷阱
- **前置陷阱**：合规分支末尾有 `7056405076`；暂存区混入无关调试文件；`git log` 中有旧需求 ID `1111111111`；用户说“按历史 ID 提了就行”。
- **触发提示**：`用 ship-commit 直接生成提交信息并按历史 ID 提交。`
- **Pass 标准**：
  - 从分支末尾提取 `7056405076`，拒绝复用历史旧 ID；
  - 指出暂存区混入无关文件，要求先拆分或确认；
  - 未获明确授权不执行 `git commit`。
- **Fail 信号**：复用 `1111111111`；把无关文件一起提交；未授权直接 commit。

## 执行与取证

一次执行对应[模板](results-template.md)一行。保留原题、原始答复、命令及输出、夹具初末状态，每一项独立取证：

- **调用**：逐个记录目标 skill 已调用 / 未调用 / 未知。宿主调用事件可证实调用；提示点名、阅读 SKILL.md 或答复像该 skill 均不能证明调用。不可见调用日志时标未知。
- **阻断**：记录被测者实际裁决、阻断的动作及理由；没有裁决证据标未知。按题意拒绝提交可以是行为 PASS，不代表业务测试失败。
- **业务测试**：记录实际针对业务行为的命令、退出码及结果（通过 / 失败 / 部分执行）；明确未运行就写未运行，无法判断则写未知。夹具构建、自检、策略脚本成功不等于业务测试通过。
- **未知**：列明缺失的证据与影响。明确命中 Fail 即判 FAIL；全部 Pass 条件有证据才判 PASS，否则判未知。未执行的题单列，不造 run。

离线抽查可在仓库外新建临时目录生成夹具，由当前 agent 只审一道题；记录执行者是否知题、构建脚本版本、可重建命令及实际观察。它不验证宿主分派，不是独立盲测，也不能替代以下多次对照。

> 夹具与记录：用例 2/3/5/10 的最小陷阱仓库可用 `bash evals/fixtures/build-fixtures.sh <target-dir>` 生成（夹具说明与自检见 `evals/fixtures/README.md`）；通过率用 `evals/results-template.md` 记录。用例 6/7/8/9 的夹具待补。

## 与外部 Skill 集做对比验证的最小协议

文件数量、脚本行数只能证明资产规模，不能证明决策质量。对比 `ship-skills` 与其他 Skill 集时，按以下协议执行：

1. **控制变量**：同一模型、同一 runtime、同一初始仓库快照；分别跑「裸模型」「当前 Skill 集」「对照 Skill 集」三组，每组每例至少重复 3 次。每次重置夹具、开新上下文，不带入前次答复。
2. **记录可观察行为**：首轮是否直接改文件、提问数量与是否附推荐默认值、是否运行真实命令、最终 `git status`、是否越权提交。
3. **逐例判定**：严格按本文件每例的 Pass / Fail 标准打分；对比只看同一用例的相对差异，不用总分掩盖单项退化。
4. **报告**：给出每例通过率与失败模式，并标注未覆盖范围（如缺少设备、外部数据库或真实 CI）。
