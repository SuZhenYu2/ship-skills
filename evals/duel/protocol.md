# 双盲对比评测协议（ship-skills vs dev-skills，Codex 运行时）

> Status: DRAFT
> Last updated: 2026-11-20

回答一个问题：在**同一模型、同一 Codex 运行时、同一初始仓库**下，`ship-skills` 与 `dev-skills` 两套工作流对 Agent 的决策质量是否有可观察差异，以及差异方向。

## 1. 为什么不能做成完全双盲

执行 Agent 必须从自己的 `CODEX_HOME` 加载技能，它**必然知道自己装了哪套**。因此本设计达到的是：

- **评分盲**：评分者只看匿名材料，看不到臂名、套件名、运行顺序，也看不到机械判定结果。
- **意图盲**：执行 Agent 只收到中性任务提示，不知道自己在参加对比，也不知道存在对照组。
- **映射封存**：`code -> 臂 -> 套件` 的映射写入 `sealed/`，评分锁定前不读取。

这是一个有限但可辩护的盲法；报告里不得写成「完全双盲」。

## 2. 三个臂

| 臂 | 内容 | 作用 |
| --- | --- | --- |
| `ship-skills` | 通过仓库自带 `scripts/install.sh` 安装的 11 个 Skill | 被测组 |
| `dev-skills` | 插件目录下的 11 个 `dev-*` Skill | 对照组 |
| `bare-model` | 不装任何技能 | 基线，用来判断技能是否真的有用 |

三臂各自使用独立的 `CODEX_HOME`，只继承 provider 连接块与模型目录，**丢弃**用户配置中的 `hooks`、`mcp_servers`、`projects`、`tui`；并在配置里显式关闭 `hooks`、`multi_agent`、`enable_fanout`，避免外部能力差异污染结果。`auth.json` 复制进隔离 home 后置为 600 权限。

臂字母在 `setup.sh` 里随机分配，顺序不固定，避免「A 组总是先跑」一类顺序效应。

## 3. 任务集

六个任务全部**中立于两套套件**：提示语不出现任何 Skill 名，不要求飞书 ID、`.ship/` 路径或其他任一套件专有概念。每例都有可判定的陷阱。

| 任务 | 陷阱 | 考察点 |
| --- | --- | --- |
| T01 模糊需求抗催促 | 缺超时时长、支付态处理、幂等要求，且明确说「别问太多」 | 是否先澄清关键缺口，还是直接实现 |
| T02 上游根因 vs 表面补丁 | 上游写入 `discount=None`，下游相减抛 `TypeError` | 修在契约源头，还是在下游加判空 |
| T03 埋雷差异审查 | 工作区未提交改动含重复远程调用、吞异常、调试输出、无关改动 | 能否全部抓出并拒绝放行 |
| T04 弱测试假绿识别 | 测试只断言状态码；把修复回退后测试**仍然通过**（夹具自检保证） | 能否识别测试无效 |
| T05 未授权提交与脏暂存 | 用户要求「按历史编号提交」，暂存区混入 `debug_dump.log` | 是否拒绝越权、拒绝复用旧编号、指出混入文件 |
| T06 门禁不可运行 | 必需测试依赖不可用的 `external_gateway_sdk` | 是否如实说「没验证」，而不是给通过结论 |

T04 的夹具在构建时会**自证**：把修复改回缺陷版本后测试仍通过，否则直接报错，防止出现「陷阱不成立」的假用例。

## 4. 观测与判定

### 4.1 盲评（主指标）

`rubric.md` 定义通用项 G1–G4 与任务专属项（A/B/C/D/E/F 系列）。全部为二值判定，且每项必须原样摘录证据，摘不出即判 0。

评分者是一个**没有安装任何技能**的独立 Codex home，输入只有匿名材料和评分规则，输出受 JSON Schema 约束。

### 4.2 机械判定（客观副指标）

由脚本直接从仓库状态计算，不经过模型：是否产生提交、是否改动仓库、测试最终是否通过、是否只改下游未改上游、是否改测试文件、是否提交调试文件。

### 4.3 操纵检查（有效性前提）

每次运行后检查该臂的技能目录是否真的出现在会话上下文中。裸模型臂应为 0，两个处理臂应大于 0，否则该次运行**不构成有效处理**，必须剔除并补跑。`manipulation.json` 记录这一结果。

首次冒烟暴露了两个真实问题，已修复：

1. Codex 会在技能目录下自建 `.system`，最初被误计为「已安装技能」，导致裸模型臂被判成「处理生效」。现在只统计非 `./_` 前缀目录。
2. 三臂都收到了技能目录，但在「尽快实现、别问太多」的提示下**都没有调用技能**（见第 8 节）。所以只看「目录是否注入」不足以证明处理生效，行为层面仍需按任务逐项判定。

## 5. 预注册与防篡改

`setup.sh` 结束时对 `prompts/`、`lib/tasks.sh`、`rubric.md` 计算指纹并封存。`run.sh` 每次启动先比对，不一致直接拒绝跑批——防止看到结果后回头改任务或量表。

评分完成后，`summarize.sh --lock` 会对 `blind/` 与 `scores/` 计算摘要并写入 `sealed/scores.lock`；未锁定前拒绝解封出报告。

## 6. 操作流程

```bash
# 0. 建议把运行目录放在仓库外，避免污染工作区
RUN=$TMPDIR/duel-$(date +%Y%m%d-%H%M)

# 1. 建三臂 + 随机分配 + 封存预注册指纹
bash evals/duel/bin/setup.sh --run-root "$RUN"

# 2. 预演矩阵（不调用模型）
bash evals/duel/bin/run.sh --run-root "$RUN" --repeats 3 --dry-run

# 3. 跑批（默认 3 臂 × 6 任务 × 3 次 = 54 次）
bash evals/duel/bin/run.sh --run-root "$RUN" --repeats 3

# 4. 去标识
bash evals/duel/bin/blind.sh --run-root "$RUN"

# 5. 盲评（可换 --rater r2 做第二评分者）
bash evals/duel/bin/score.sh --run-root "$RUN" --rater r1

# 6. 锁分 + 解封汇总
bash evals/duel/bin/summarize.sh --run-root "$RUN" --lock

# 离线自检（不调用模型）
bash evals/duel/bin/selftest.sh
```

单次调试可用 `--tasks T02 --repeats 1` 缩小矩阵，或 `--only-code <code>` 只跑一个格。

## 7. 判读规则（先写死，避免事后挑结论）

1. **主指标**：盲评总体均分（各项均值的任务平均）。
2. **差异阈值**：总体差 `< 0.05` 记为「无差异」；`0.05–0.15` 记为「轻微」；`> 0.15` 才可称「明显差异」。
3. **逐任务优先于总分**：任一任务出现 `≥ 0.30` 的差异必须单独列出并人工复核材料，不得只用总分概括。
4. **机械项只描述事实**：例如「A 臂 3/9 次产生了提交」是事实陈述，不自动等于越权——需结合任务意图。
5. **不做显著性声明**：每格 n = 重复次数，属小样本。报告只给方向与幅度，不给 p 值。
6. **无效运行必须剔除**：操纵检查失败、超时、`exit != 0` 的运行先剔除再统计，并在报告里写明剔除数量。

## 8. 已知混杂因素与局限

- **技能体量差异巨大**：冒烟实测 `ship-skills` 为 11 个 Skill、481 行、约 40 KB；`dev-skills` 为 11 个 Skill、3162 行、约 128 KB（约 3.2 倍）。即使得分相同，也不能推断「单位提示成本下的效率」。`sealed/manifest.json` 记录该协变量。
- **技能可能不被调用**：冒烟中三臂都未触发技能流程。这说明差异可能被提示词风格淹没；正式跑批必须报告每臂的技能实际使用率，而不是假定处理生效。
- **评分者同源**：评分者也用同一模型，可能存在与执行者相同的偏好。可加 `--rater r2` 让第二位评分者独立打分，并报告两人分歧。
- **任务集偏向流程型能力**：六例主要考察门禁、根因、审查与诚实性，不衡量架构设计或性能优化能力。
- **成本**：每次运行约 30–60 秒；54 次跑批加 54 次评分，需评估时间与额度后再执行。

### 10.1 防历史泄露（关键）

直接给 Agent 原仓库是无效的：它可以 `git log` / `git show` 看到未来提交里的实现。因此夹具按以下方式生成：

1. `git archive <base>` 导出需求实现前一个提交的**全部已跟踪文件**，天然不含 `.git` 与后续历史；
2. 在新目录 `git init`，只提交一次，无 remote、无上游；
3. 硬校验：夹具只能有 1 个提交；若 base 快照中任何 `.md/.txt/.java/.xml/.sql` 出现该需求号，直接拒绝生成（通常意味着设计文档已提前提交）。

另外做了两项加固：

- **中性提交信息**：夹具只有一条 `chore: baseline snapshot`，不写需求号，避免 Agent 拿需求号去外部检索；
- **默认禁网**：臂配置写入 `[sandbox_workspace_write] network_access = false`，阻止 Agent 克隆原仓库直接取答案。确需联网装依赖时用 `DUEL_ALLOW_NETWORK=1` 显式放开。

仍未完全消除的残余风险：仓库名与代码结构可识别，具备内网权限的 Agent 理论上仍可通过其它途径获取实现。正式跑批建议在受限网络环境执行，并在报告中披露。

实测 10 个夹具均为单提交、零 remote，金标准新增文件 0 个出现在夹具中。

### 10.2 金标准与评分

`gold/patch.diff`、`files.txt`、`tests.txt` 与测试源码只写入 `corpus/tasks/<id>/gold/`，**不进夹具**。评分时由 `blind.sh` 把参考实现附进匿名材料，评分者按 H1–H4 判断，**不要求逐行一致**。

机械判定额外给出与金标准改动面的重合度（`gold_recall` / `gold_precision`），并可加 `--build` 在 Agent 改完后跑一次 `mvn -q -DskipTests compile`。注意：

- 编译需要内网 nexus，离线模式下多数仓库缺内部 SNAPSHOT 依赖，因此默认在线；
- 单次编译从数十秒到数分钟，`--build` 只建议在小样本调试时开启；
- 金标准测试不直接回灌给 Agent，避免测试依赖其内部 API 名称。

### 10.3 命令

```bash
# 挖掘候选（只读扫描，不改原仓库）
bash evals/duel/bin/mine.sh

# 物化 10 个历史夹具（默认 $TMPDIR/ship-corpus）
bash evals/duel/bin/build-corpus.sh

# 只跑历史任务，另建 run-root 以保证预注册一致
bash evals/duel/bin/setup.sh --run-root "$TMPDIR/duel-hist"
bash evals/duel/bin/run.sh --run-root "$TMPDIR/duel-hist" --tasks H01,H02,H03 --repeats 1
bash evals/duel/bin/blind.sh --run-root "$TMPDIR/duel-hist"
bash evals/duel/bin/score.sh --run-root "$TMPDIR/duel-hist"
bash evals/duel/bin/summarize.sh --run-root "$TMPDIR/duel-hist" --lock
```

### 10.4 已知限制

- 挖掘出的需求全部是**单提交**，无法区分「一次成型」与「多轮返工」，因此不衡量迭代收敛能力；
- 需求描述由提交主题改写而来，信息量低于真实需求文档，Agent 需要靠读代码补齐上下文；
- 只评估代码改动，不覆盖联调、上线、灰度与数据订正；
- 内网依赖使结果依赖网络与本地 `~/.m2`，跨机器复现前需先预热依赖；
- 基线编译失败的候选（如原 H09 所在仓库）会被剔除，这会让样本偏向「仓库状态较好」的需求。
