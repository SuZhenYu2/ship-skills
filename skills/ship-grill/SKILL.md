# ship-grill（需求与方案深度拷问 + 长期上下文沉淀）

> 路径解析：本 Skill 内所有 `references/`、`docs/`、`scripts/` 路径均相对本 Skill 目录解析。

> 对应 `dev-grill-docs` 能力。目标是**在写第一行代码之前对想法做压力测试**，把隐性假设、术语歧义和不可逆权衡暴露在设计阶段，而不是留到返工或线上事故里。

## 何时使用 / 何时不用

- **使用**：新需求存在关键缺口、方案有多种不可逆权衡、团队对核心业务术语/状态定义容易歧义，或需要为多 Agent 协作建立长期契约。
- **快捷模式（`--spec-only`）**：已清楚业务术语、无需沉淀 `CONTEXT.md` 或 ADR，只想快速对齐并输出 `.ship/specs/<slug>.md` 时，可直接传 `--spec-only`（等价于调用 `ship-spec`）。
- **不用**：单文件、范围明确、无外部契约或不可逆风险的小改动（直接走 `ship-tdd` / `ship-verify`）。

## 反偷懒红线（Red Flags）

- **禁止顺着用户的话敷衍点头**：必须真正扮演资深评审者做压力测试——如果用户的想法存在并发竞态、状态机漏洞、兼容断裂或隐性假设，必须直接指出并追问，不能用“听起来很合理”敷衍跳过。
- **禁止刷题式过度拷问**：每轮拷问聚焦 **3~5 个最容易导致返工的致命问题**，每个问题附带**推荐默认方案与权衡代价**；可逆的局部实现细节不追问。
- **禁止滥写 `CONTEXT.md` 和 ADR**：只在确有价值时写入（`CONTEXT.md` 只记跨需求复用的稳定词汇与领域边界；ADR 只记难以逆转或影响全局的架构/技术决策）。
- **禁止越权写业务代码**：本 Skill 阶段严禁修改任何业务源码。

## 执行步骤

### Step 0 — 加载既有上下文
1. 遵循 `references/dev-baseline.md`。
2. 检查并读取项目既有长期记忆（若存在）：
   - 项目根目录 `AGENTS.md` 与 `CONTEXT.md`（复用既有稳定术语，避免造新词冲突）；
   - `docs/adr/` 下相关历史 ADR；
   - 受影响模块的核心接口与数据模型（跨多模块时可按 `docs/multi-agent-policy.md` 派 1~2 个只读 `Scout` 摸底）。

### Step 1 — 压力拷问（Grilling）
围绕 5 个高危维度审视用户想法，仅挑出真正存在缺口或冲突的 **3~5 个核心问题** 一次性抛出（每题给出推荐默认值）：
1. **隐藏假设与反例**：在什么边界输入、空数据、并发重入或部分失败场景下，当前想法会直接崩掉？
2. **术语与状态边界**：涉及的核心名词、状态枚举、归属权是否与仓库既有 `CONTEXT.md` / 代码一致？
3. **范围与非目标（Scope / Non-Goals）**：明确哪些**这次不做**，防止实现蔓延。
4. **不可逆权衡与兼容性**：是否涉及持久化 Schema、对外协议、迁移或灰度兼容？有没有更轻量的替代方案？
5. **飞书需求 ID 与验收标准**：确认关联的 `<req-id>` 及可自动化验证的验收条件。

> 若存在未决致命缺口，暂停在拷问阶段等待用户拍板，**0 行代码修改，不写残缺文档**。

### Step 2 — 落盘三类按需产物
关键决策对齐后，按需落盘：

1. **必选：Spec 契约文档** → `.ship/specs/<slug>.md`
   - 文档头固定包含：`> Status: DRAFT | ALIGNED | IMPLEMENTED | STUCK`、`> Source: <需求来源>`、`> Last updated: <YYYY-MM-DD>`；正文固定包含：背景与目标（含飞书 `<req-id>`）、范围与非目标、核心术语与业务规则、接口/数据契约变化、异常/并发/兼容性要求、已拍板的关键权衡、可验证验收标准。
   - `Status` 枚举与语义见 `references/dev-baseline.md` 的产物状态枚举；`IMPLEMENTED` 仅在已有实现证据时保留。
2. **按需：稳定领域词汇** → 项目根目录 `CONTEXT.md`（`--spec-only` 跳过）
   - 仅当本次对齐确立了**后续多需求会反复复用**的稳定业务术语、状态机定义或系统边界时，以增量追加/更新方式写入 `CONTEXT.md`（不破坏原有条目）。
3. **按需：架构决策记录（ADR）** → `docs/adr/<nnnn>-<slug>.md`（`--spec-only` 跳过）
   - 仅当本次拍板了**难以逆转或影响全局**的技术/架构决策时，按现有最大编号递增生成（如 `docs/adr/0001-order-cancel-idempotency.md`），固定包含：Status（Accepted）、Context、Options Considered、Decision、Consequences。

## 完成标准

- 未对齐前：精准抛出 3~5 个压力拷问（含推荐默认值），无任何业务代码改动。
- 对齐后：`.ship/specs/<slug>.md` 已落盘，明确说明本次是否更新了 `CONTEXT.md` / 新增了 ADR 及原因，并提示下一步进入 `ship-plan`（复杂/高风险）或 `ship-tdd`（中低风险）。
