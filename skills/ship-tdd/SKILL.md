# ship-tdd（测试驱动与受控实现）

> 路径解析：本 Skill 内所有 `references/`、`docs/`、`scripts/` 路径均相对本 Skill 目录解析。

## 核心原则

- 遵循 `references/dev-baseline.md`。若有 `.ship/specs/<slug>.md` 或 `.ship/plans/<slug>.md`，严格以此为准。
- **按风险选测试节奏**：
  - **新行为 / 关键逻辑变更**：优先编写能验证验收条件的失败测试（Red），再写最小实现使其通过（Green），最后做必要清理（Refactor）。
  - **重构（不改外部行为）**：先确认已有行为测试覆盖（不足则先补表征测试），再小步重构。
  - **低影响改动（文案、日志、注释、配置微调）**：不强写无意义单测，直接实施并做对应检查。

## 执行步骤

1. **确认范围与契约**
   - 检查是否存在共享契约变更；若处于 Multi-Agent 模式，严格遵守 `docs/multi-agent-policy.md`：
     - `Lead` 先完成契约冻结并确认可编译。
     - `Builder` 仅修改分配给自己的文件白名单，绝不越界修改共享契约、构建配置或执行 Git 写操作。
2. **编写测试与实现**
   - 新增行为先确认 Red 来自缺失行为本身，而不是测试夹具、导入或环境错误，再写最小实现转绿。
   - 测试应覆盖正常路径、关键边界条件与异常流，避免只测无意义的 Mock 恒等式。
   - 遵循当前项目的代码风格、错误处理与目录约定，不顺手重构无关代码。
3. **本地自测**
   - 按 `references/dev-baseline.md` 中的命令探测顺序运行相关单测，确保当前模块编译通过且新增/相关测试全部通过。
4. **交接下游**
   - 实现与自测完成后，提示进入 `ship-verify`（或在多 Agent 模式下移交干净上下文的 `Critic` 做独立边界测试与验证取证）。

## 禁止事项

- 禁止为了通过测试而削弱断言、跳过失败用例或悄悄修改验收标准。
- 禁止在本 Skill 中直接执行 `git commit` 或 `git push`。
