# 通用工程风险审查清单（Review Checklist）

本清单供 `ship-review` 及 Multi-Agent 中的 `Critic`（或独立 `Auditor`）使用。审查目标不是纠结代码格式化风格，而是拦截会导致线上事故、数据损坏或维护灾难的真实风险。

## 1. 严重级别定义

- **BLOCKER（阻断）**：会导致数据错误、资金/权限漏洞、崩溃、死锁、向后不兼容破坏、测试未通过或违反必选提交规范。**存在任意 BLOCKER 时不得放行提交。**
- **MAJOR（高风险）**：存在明显性能隐患、边界条件漏处理、关键路径缺测试、异常被静默吞掉或资源潜在泄漏。未接受的 MAJOR 必须判 `BLOCKED`；延期须记录用户对该项风险的明确接受，不得以提交授权代替。
- **MINOR（建议）**：可读性、局部抽象优化、注释或非关键测试补充。不阻断提交。

## 2. 六大审查维度

### A. 正确性与数据一致性
- 改动是否完整覆盖 `.ship/specs/<slug>.md` 或用户提出的所有验收条件？
- 写多张表/多份状态时，事务边界或补偿逻辑是否完整？（如是否存在事务内调外部耗时 IO、局部失败导致脏状态、或事务失效风险）
- 空值、零值、空集合、超大输入、时区/精度（如金额浮点运算）、边界状态机跳转是否已处理？

### B. 并发、幂等与重入安全
- 写接口、消费消息或定时任务是否具备幂等性（重复请求/重放是否产生重复数据或重复扣减）？
- 共享可变状态、缓存读写、分布式锁（加锁粒度、过期时间、误删他人锁）是否存在竞态条件？

### C. 性能与资源管理
- 循环内是否存在数据库查询 / 外部 RPC 调用（N+1 问题）？
- 新增或修改的查询是否命中合理索引，是否存在大表全扫描、无分页拉全量、或大对象常驻内存？
- 文件句柄、网络连接、锁、流、子进程或定时器是否在异常路径下也保证正确释放？
- 提前拒绝超大请求体或流式输入时，是否避免服务端等待未读 body？HTTP/1.1 慢速或分块上传能否及时返回 413 并关闭连接？
- 是否按实际读取字节判断大小，而不是信任可伪造或已过期的 `Content-Length`？

### D. 错误处理与可观测性
- 是否存在吞掉异常（空 `catch` / 忽略返回 `err`）导致失败静默？
- 对外返回的错误码/提示是否清晰且不暴露内部堆栈或敏感信息？
- 关键状态流转与异常分支是否有足够定位问题的结构化日志，且未打印密码/Token/隐私明文？

### E. 兼容性与契约边界
- 对外 API、RPC 协议、消息格式、配置项或数据库 Schema 变更是否向后兼容（灰度发布期间新旧版本共存是否安全）？
- 持久化变更（DDL / Migration）是否有安全回滚策略，是否会造成长时间锁表？

### F. 改动范围、验证证据与合规
- `git diff` 中是否混入了无关格式化、临时调试日志、注释掉的废代码或误改的配置文件？
- 是否具备 `ship-verify` 的真实构建与测试通过证据？核心行为改动是否有对应的自动化测试覆盖？
- 新增或修改的测试是否能在缺陷复现或修复回退时失败？禁止用状态码、Mock 恒等式或“不抛异常”冒充核心行为覆盖。
- 若必需验证门禁因环境限制未运行，是否明确标注 `PARTIAL` / `INCOMPLETE`，而不是给出 `READY`？
- 若项目启用了语言专项清单（`AGENTS.md` 或 `references/stacks/<lang>.md`），对应红线项是否已逐一核对？
- 当前 Git 分支与计划的 Commit Message 是否符合 `references/git-branch-policy.md`？

## 3. 输出格式要求

每条问题必须给出可定位、可执行的结论：

```markdown
- **[BLOCKER|MAJOR|MINOR]** `<file>:<line>` — <一句话问题结论>
  - **风险机理**：<什么条件下会触发什么后果>
  - **修改建议**：<最小可行修复方案>
```

最终必须给出明确裁决：`READY`（同树 PASS、必需证据齐全，无 BLOCKER 或未接受的 MAJOR）、`BLOCKED`（附阻断项清单）或 `INCOMPLETE`（无已知阻断，但必需验证门禁未运行或结果为 `PARTIAL`，附补齐命令）。
